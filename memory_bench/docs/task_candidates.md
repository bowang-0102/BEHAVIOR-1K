# Memory Bench：8 个日常活动任务与资产核验

本版保留四类、每类两个，共 **8 个任务**。每项先确定一个日常活动，再把活动拆成有实际用途的 Key 和 Query；记忆需求来自活动中需要延续的位置、状态或物体对应，而不是为了制造记忆题增加搬动。

**SP 保留两种形式：SP1 是“收进柜子并遮住 → 稍后取用”，SP2 是“借出 → 归还原处”。** 删除“试放后立即收回”的整合流程，以及单纯要求两件物体交换位置的更新流程。状态任务也不以重新开一次门作为唯一收尾目标，而是继续完成物品收纳。

**核验边界（2026-11-04）：** 文中明确列出的现有家具 ID、房间、模型与资产文件已做静态核对。新增物体实例、可用落点、抓取、遮挡、开合、导航与完整序列尚未验收；当前工具环境无法连接 NVIDIA 驱动。本文件是具体设计，不是八项任务已经可以采集的证明。此前的资产检查结论不能自动覆盖本版新增加的柜内取放、篮内放置和腾空区域。

## 1. 先看活动，再看记忆类别

| 编号 | 类别 | 日常活动 | Key 做什么 | Query 接着做什么 |
|---|---|---|---|---|
| SP1 | L1 · Spatial Recall / 空间记忆检索 | 食材收纳与后续备料 | 把小苏打收入一个下柜并关门 | 需要备料时取出，放到操作台 |
| SP2 | L1 · Spatial Recall / 空间记忆检索 | 借用客厅饮具后归位 | 从一处收纳位拿杯子到书桌备用 | 将借出的杯子归还原收纳位 |
| ST1 | L1 · State Recall / 状态记忆检索 | 分段完成工具间收尾 | 离开前暂时关好原先打开的柜门 | 把待收纳手电筒放进原先在整理的柜子并关门 |
| ST2 | L1 · State Recall / 状态记忆检索 | 暂停后继续打包工具箱 | 暂停整理，合上原先打开的工具箱 | 继续往原先打开的工具箱装入电钻并合盖 |
| MI1 | L2 · Memory Integration / 多片段记忆整合 | 咖啡用品准备与归位 | 分别取杯子、取糖罐，备到同一操作区 | 收尾时分别归还各自原位置 |
| MI2 | L2 · Memory Integration / 多片段记忆整合 | 客厅茶歇用品准备与归位 | 分别从两组收纳位取杯子、糖罐到书桌 | 结束准备后分别归还原收纳位 |
| MU1 | L2 · Memory Updating / 动态记忆更新 | 餐后收杯与腾出备餐区 | 收起早餐桌上的待洗杯；随后整理台面腾出操作区 | 找到本轮收起的待洗杯，放进水槽 |
| MU2 | L2 · Memory Updating / 动态记忆更新 | 客厅整理与集中收杯 | 收起书桌上的待洗杯；随后腾出柜顶中央摆书区域 | 把本轮收起的待洗杯放入收杯篮，准备送洗 |

这八项是日常活动中的**准备、暂存、收纳和收尾子任务**，不额外模拟喝咖啡、烘焙、维修或洗杯来增加遥操负担。不能把没有执行的饮用、维修、擦洗写成轨迹中已经发生的事件。“待洗杯”是任务开始时给定的用途角色，详见更新类定义。

共同原则：

1. **每个 Key 都要产生可说明的家务结果。** 例如食材已收好、用品已备齐、柜门不再挡路、工作区已腾空。
2. **Query 延续同一个活动目标。** 例如继续备料、完成收纳、恢复用品位置、集中收集待洗杯。I 是中途的其他家务，不伪装成没有录制的使用或清洁过程。
3. **不为严格凑同样的动作数增加无用搬动。** 保留必要对照，记录实际操作成本。
4. **物体和布局优先省力。** 不叠放、不精确归架、不清洗烹饪、不搬满箱；仍需试操证明是否适合。

## 2. 数量、变体和证据约束

### 2.1 片段设置

- L1：**1K + 2I + Q**；L2：**2K + 2I + Q**，相邻片段加入 Bridge，Q 最后执行。
- config 指定合法顺序，当前支持 1–3 种候选顺序；MU 保持 K₁ 在 K₂ 前。
- 所有 K/Q 同场景、同房间实例；两个 I 位于另外两个不同房间实例，优先邻近 memory room。每个 I 的操作全程限于其单个房间，不含跨房取放或通行门开关；允许使用验收合格的官方录制单房间子任务。
- 固定目标物体、Q 指令与活动目的；位置或历史状态是主要变体，顺序与答案独立分配。

### 2.2 主要变体从被测能力产生

| 类别 | 固定内容 | 主要变体 |
|---|---|---|
| Spatial Recall | 同一目标物体和活动 | SP1 的隐藏位置 A/B；SP2 的原收纳位 A/B |
| State Recall | 两个容器的位置、待收纳物体 | 初始打开的是容器 A 还是 B；Q 时都关闭 |
| Memory Integration | 两件固定用品 | 物体 X 的原位置 A₁/A₂ × 物体 Y 的原位置 B₁/B₂，四个独立组合 |
| Memory Updating | 同一待洗杯 X、同一备用杯 Y | X 起点 A/B × 后续放到 A/B，覆盖 A→B、B→A、A→A、B→B |

`A/B` 是文档和评价中的位置代号，策略通过家具与环境参照识别，不能读取答案 ID。MI 不限定两个物体一一占满两个互斥位置；否则一条位置事实可能推导另一条。

### 2.3 家务合理性与信息独立性都要通过

“取用品 → 用后归位”比试放再收回自然，但不能因此省略观测审计：

- K₁ 不得提前给出物体 Y 的原位置，K₂ 不得再次给出 X 的原位置；全部相机、语言、动作、I 和 Bridge 都要检查。
- MI1 使用关闭的柜门遮住糖罐来源；MI2 使用分开的观察方向与局部接近路线，尚需渲染验证。**若 MI2 轨迹提前拍到了另一件物体的来源，就不算两个必要 Key，必须重新安排路线或布局，不能用“两个取物任务”掩盖信息重复。**
- SP2、ST 和 MI 在 Q 时不能留下可直接恢复历史答案的空位标记、门角差异或物体摆放偏差。
- 进入 Key 前的 Bridge 不能提前暴露原位置或原状态；需要把首次获取证据的观察纳入相应 Key，并实际检查桥接视野。
- Key 指令若给出柜子位置或整理落点，应记录为语言证据，不宣称只测视觉记忆。

SP1 的位置在 Q 时仍存在，忘记后可以逐柜搜索。因此区分首次正确选柜、额外开柜次数与最终取回成功；它与历史位置归还任务的评价不能混为一谈。

## 4. Spatial Recall：收纳后取用 + 借用后归还

### SP1．收好小苏打，之后取出备料

- **活动与场景：** 单层厨房的食品收纳与后续备料，参考 `storing_food` 的“台面食材入柜”结构。
- **对象与位置：** 唯一小苏打盒 `mb_sp1_soda`，模型 `box_of_baking_soda/pskrgy`；A=S-GA，B=S-GB；起点与取回目的地均为 S-A。
- **K：** “把操作台上的小苏打收进指定的下柜，关好柜门。”根据 A/B 变体把盒子放入相应柜内；出口两柜全关，盒子不可见。
- **Q：** “把之前收好的小苏打取出来，放到操作台上备料，并关好柜门。”Q 不给出柜子答案。
- **主要变体：** 同一盒小苏打的隐藏位置 A/B。
- **活动结果：** K 完成食品归柜，Q 完成后续备料的取材；不额外要求做饭。
- **判分：** 首次选柜是否正确、错误开柜与额外搜索次数、最终盒子是否在 S-A 且两柜全关。允许搜索补救，但不把补救成功等同于记住位置。
- **待验收：** 指定内层落点、开关门、盒子窄边抓取及头部/手腕相机的遮挡；不能因“下柜”就认定好操作。

### SP2．借出客厅杯子，结束后归还

- **活动与场景：** 上层客厅的饮具取用与归位；取用和归位是实际记录的动作，不插入虚构的饮用或洗杯片段。
- **对象与位置：** 唯一杯 `mb_sp2_cup`，模型 `coffee_cup/nbhcgu`；原位置 A=U-A / B=U-B，借用位置 C=U-C。
- **K：** “从矮书柜顶部拿一个杯子到书桌上备用。”初态只有一只任务杯，在 A/B 之一；K 结束杯子在固定书桌区域。
- **Q：** “把刚才借到书桌上的杯子归还到原来的收纳位。”
- **主要变体：** 原收纳位置 A/B；目标物体和 Q 固定。
- **活动结果：** K 备好饮具，Q 恢复客厅用品摆放；不要求为了记忆先试放到陌生位置再收回。
- **判分：** 杯子回到正确柜顶并稳定松手；只放在该柜内部层板不算成功。
- **待验收：** 杯体抓取、柜顶支撑、书桌灯具避让，以及 Q 当前布局是否一致、无来源痕迹。

## 5. State Recall：记住暂停前的工作状态，继续完成收纳

两项均固定容器位置，初始恰好一个打开；K 暂时关闭，Q 时两者均关闭。正确目的容器由**历史开合状态**确定，不是物体之前放在哪个容器，也不是当前哪只容器有空位。

### ST1．关柜暂停，回来继续收纳手电筒

- **活动与场景：** 单层工具间收尾。初始打开的柜子是本轮正在整理的柜子；唯一手电筒还在 W-C，尚未归柜。
- **对象：** 现有 W-A/W-B 两柜，新增 `mb_st1_flashlight`，模型 `flashlight/jtrbkc`。
- **K：** “先把打开的柜门关好，离开工具间时不要挡住通道；手电筒留在台面，回来继续收纳。”入口一柜开、一柜关，出口两柜全关。
- **Q：** “继续收尾，把台面上的手电筒放进开始整理时开着的那个柜子，再关好柜门。”
- **主要变体：** 初始开着的是 W-A 或 W-B；手电筒初始位置固定，两柜的内部可用空间不随答案变化。
- **活动结果：** K 暂时关闭柜门，Q 真正完成一件工具的归柜，不以把柜门重新打开为终点。
- **判分：** 手电筒在历史打开的柜内、两柜全关、机器人松手。错误柜里有空位不能作为替代正确答案。
- **待验收：** 门柄可达、内部前侧落点和手电筒滚动。只收一件工具，不要求整理满柜。

### ST2．合盖暂停，回来继续装工具箱

- **活动与场景：** 单层工具间的工具箱打包，参考 `outfit_a_basic_toolbox`，只保留一个电钻的收纳。
- **对象：** W-C 上两只 `toolbox/redmtl`，计划名 `mb_st2_toolbox_a/b`；唯一 `mb_st2_drill`，模型 `drill/nzgmza`，留在独立抓取区。初始打开的箱子表示本轮正在装的箱子。
- **K：** “暂停打包，先合上打开的工具箱，电钻留在台面，之后继续装。”结束两箱全关，位置不动。
- **Q：** “把台面上的电钻装进暂停前开着的那个工具箱，并合好箱盖。”
- **主要变体：** 历史开箱对象 A/B；电钻与两箱位置固定，两箱容量均足够，不靠容量推断答案。
- **活动结果：** K 保护暂存工具，Q 完成剩余工具的装箱；不要求搬箱或启动电钻。
- **判分：** 电钻在正确工具箱内、两箱都关闭、箱体仍在各自支撑区。
- **待验收：** 盖缘可抓、箱底不滑、两箱扫掠不冲突、电钻抓握与合盖空间。第二只箱子和重复模型映射尚未实现。

## 6. Memory Integration：两次准备，联合归位

## 7. Memory Updating：家务改变位置，继续追踪待处理物品

### 7.1 共用机制：清出工作区，而不是为了更新而交换

两项均有同款、同尺寸、同材质的两只空杯：**X 是本轮从使用区收起的待洗杯，Y 是备用杯。** X/Y 的任务角色与内部实例固定，变化只来自位置。K₁ 指令通过来源明确指出 X；“待洗/备用”是初态给定的家务角色，不假装已在轨迹里喝过水，也不新增清洗、脏污粒子或隐藏污渍状态。

- K₁：从使用区收起 X，暂放到 A/B 中的一个位置；Y 在另一个位置。每个位置起初均占用了后续家务需要的工作区域。
- K₂：**把两只杯子移出工作区域，为备餐或整理书籍腾出空间。** A、B 各有一个经过验证的侧边暂存落点，杯子可留在同一家具的侧边，也可移到另一家具的侧边。每只杯子只抓放一次，两个分支都有实际的“工作区清空”结果。
- Q：找到本轮收起的 X，送入待洗目的地；Y 仍留在暂存区。

| 变体 | K₁ 后 X 所在家具 | K₂ 后 X 所在家具 | 实际含义 |
|---|---|---|---|
| U1 | A | B | 让出 A 的工作区域，暂放到 B 侧边 |
| U2 | B | A | 让出 B 的工作区域，暂放到 A 侧边 |
| U3 | A | A | 从 A 的工作区域移到 A 自己的侧边 |
| U4 | B | B | 从 B 的工作区域移到 B 自己的侧边 |

A→A / B→B 表示家具级位置不变，**不是静止不动**。两个分支各有两次抓放，不经过无用途的两个中转区；最终两处工作区域都空出来，两个侧边落点各有一只杯子。K₂ 一律按起始位置 A、B 的次序操作，不能按“先动待洗杯”暴露 X 身份；指令只给整理位置，不复述待洗/备用对应。

两个 Key 仍应必要：K₁ 决定哪只杯子属于本轮待洗对象，K₂ 决定整理后它在哪里。仅 K₂ 不知道 X 的身份；仅 K₁ 不知道后来是否换了家具。Q 的同款外观不能直接恢复身份，且每次移动全程可追踪。杯把方向、材质、固定姿态和落点偏差不得与 X 身份绑定。

**新增验收要求：** 工作区域必须是有实际用途、确实被清出的区域，不能事后画一个虚拟小框宣称完成家务。冻结布局时在场景图中标明备餐面或摆书面、两处暂存区和真实空闲面积；不放到台沿危险位置。K₂ 的目标应检查杯子离开工作区且区域已腾空。该区域评价和布局目前尚未实现，不能只用两个 `ontop` 条件代替。

## 8. Intervening 搭配与实现边界

### 8.1 选择规则：先看导航与单房间完整性，再看是否已下载

候选范围为完整 BEHAVIOR-2026 任务表；本次检查了其中落在三个目标场景的 76 项。**是否已下载仅影响后续素材准备，不影响设计入选。** 允许从官方多房间录制中提取独立、目标完整的单房间子任务；实际作为 I 的片段必须满足下列条件：

1. **操作全程在一个真实房间实例内。** 机器人入口、出口、操作过程、物体来源及目的地均属于同一 `room_id`。不能只看任务表的房间类型列表，必须核对模板绑定、BDDL 目标与最终录制轨迹。
2. **不操作房间之间的通行门，不跨房取放。** 房内柜门、箱盖的开合可以保留；去另一房间取东西、开通道门后返回的过程不能留在 I 内。
3. **优先靠近 memory room 的房间和工作区。** 比较整条编排的所有 Bridge，包括 I₁→I₂，不能只比较两个 I 各自距 memory room 的距离。优先短通路、少拐弯、少门洞、无需绕户外的组合。
4. **两个 I 仍在不同房间，且均不同于 memory room。** 允许两个 I 来自同一官方任务的不同房间片段，但必须各自有完整目标和独立操作资产。
5. **入口/出口好衔接。** 优先靠近可通行开口、机器人空手、基座停稳、双臂可收拢的边界；不选任务结束后把箱子、椅子或杂物留在门口的录制。
6. **尽量不引入额外回放难题。** 同样距离下优先刚体收纳，避免当前管线尚难恢复的清洁粒子变化、物体切分等。完整官方任务是否难遥操不是重新采集它的理由，优先寻找可复用的合格录制。

I 内的单房间约束与 Bridge 的跨房导航分开：Bridge 可以经过必要的公共走廊，但不承担开门或取放；不得把一段房间间搬运伪装成 I 内部操作。经过 memory room 时还须检查视线与保护对象，优先避开其证据区。

- **I 不开通行门，Bridge 也不开通行门。** 合格统一实例的路线必须在进入序列前就可通行，相关门状态在整条序列中保持兼容。需要开启的门只能作为明确的实例初态准备，并与源片段及保护集合核对；不能在拼接时偷偷开门或覆盖源状态。当前准备流程默认不自动打开房间门。
- 上层卧室 0 的入口门为 `door_pxhbim_1`，基座位置约 `(−2.53,0.69)`；客厅北侧浴室入口候选为 `door_pxhbim_0`，约 `(−0.21,1.24)`。stable JSON 中二者关节接近关闭初态，**原样加载不能被当成已有通路**。
- 上层还有一个需明确处理的标注差异：`door_pxhbim_0` 的 `in_rooms` 含 `bathroom_1`，但房间分割图与任务 5 的绑定使用 `bathroom_0`。这里按实际位置把它列为入口候选，最终须在统一实例中确认，不只根据门的字符串标签选择路径。若无法取得一致可通行的实例，5 不冻结为可用 I；28 可作为另一直接相邻卧室的备选重新检查，不能默认已通过。
- 单层优先经内部客厅/走廊连接；下层优先经厨房、客厅、走廊连接。不要为了避开家具改走花园、车库或需要开启外门的路径。
- 真正排名使用 `上一段 exit → 下一段 entry` 的可通行路径：记录所有 Bridge 的累计路程、最长一段、转弯与门洞次数，以及收臂/展臂碰撞。任务工作区均值只用于前期筛选。
- 录制结束时的鞋、玩具、袋子、箱子与椅子不得堵住未来路线；必须用继承 I 终态后的世界验证，不能只检查空场景地图。相邻房间也可能因家具或门状态而难衔接。

### 8.5 单房间切段的验收与代码缺口

当前只确定设计，没有生成 54-D / 54-L 可用切段。此前抽查的一份 task-0054 HDF5 含完整 `demo_0`、动作和序列化状态；尚未解码验证其可裁区间，不能据文件存在声称两段已经可用。

每个子任务须保存原始 task ID、activity、HDF5、demo、连续半开区间 `[start,end)`、局部指令与目标、单房间物体集合，以及真实 `state[start]` / `state[end]`。入口和出口必须空手停稳，区间内机器人全程留在指定房间；不得在一次抓取或跨门动作中间切断。只有达到声明的局部目标才算一个完整 I。

**现有实现不能只改 config 的 room_id 就支持这件事：** [`inspect_source()`](../utils/recordings.py) 当前使用整条活动的绑定集合，并返回整段 `[0,N)`；[`prepare_intervent.py`](../collection/prepare_intervent.py) 也按完整活动筛素材。54 的全量绑定跨两个房间，直接交给现有单房间校验会失败。

接入时需显式支持“原始来源活动 + 局部子任务定义”，传递区间、局部绑定/读写范围、正确入口快照与独立目标；[`describe_intervent()`](../utils/task_segments.py) 还需使用局部指令，不能只把原活动名转成句子。不能删除完整录制里另一个房间的绑定却保留跨房动作来绕过校验。本次仅更新设计文档，不声称这些接入已实现。

新的待准备素材包括 21、59、5；54、0、22 即使已有本地目录，也必须重新检查合格区间和完整轨迹。下载状态不改变上述优先顺序。

### 8.6 仍需实现和验证

- **新版实例与活动定义：** 所有 `mb_*` 对象和新任务配置尚未生成。旧小苏打吊柜代码与旧杯子更新代码均不强制沿用。
- **同款物体映射：** [`prepare_session.py`](../collection/prepare_session.py) 的 `_shared_task_bindings()` 当前拒绝同一片段内重复新增模型。ST2、MU1、MU2 仍需显式实例对应或统一场景预建绑定，不能给 MU 换不同外观来绕开限制。
- **状态继承：** [`MemoryTask`](../tasks/base_task.py) 的 `variant_init` / `variant_goal` 检查条件，不自动构造初态；K 的结果必须真实继承到 Q。
- **评价扩展：** SP1 首次选柜与搜索成本、柜顶范围、MU 工作区腾空和首次目标选择尚需评价实现；只检查家具上的 `ontop` 不充分。
- **语义与物理分别验证：** “正在整理的柜子”“待洗杯”等角色由任务初始上下文明示；实际动作必须达到明确的放置、收纳、关门或腾空目标，不能只补一句背景故事。
- **两 Key 的必要性：** [`Session`](../session.py) 能检查数量与依赖，不能证明信息独立；MI2 的观察隔离尤其需要逐帧验证。

## 9. 冻结这八项前的验收

按以下顺序验收，不再扩充为 16 个候选：

1. **活动是否成立：** 去掉“这是记忆测试”的前提，人是否仍有理由执行每一步？K 的结果是否有实际用途，Q 是否完成后续家务？没有用途的试放、搬回和交换直接删除。
2. **动作是否省力：** 先试单次抓放与开合，再逐变体试完整 K/Q；记录掉落、重抓、碰撞、底盘调整、人工救场和时长。下柜深探、难开盖、篮内干涉或台沿放置不能靠故事合理化。
3. **物理结果是否真实：** 收好、备齐、关门、归位、集中待洗、腾出工作区都须有可评价结果；不声称完成未执行的饮用、维修或清洗。
4. **信息是否有效：** SP1 检查隐藏与搜索；SP2/ST/MI 检查历史信息在 Q 中是否已不可恢复；MU 检查当前外观不能辨认目标、K₂ 运动又始终可追踪。
5. **两个 Key 是否必要：** 移除任一 Key 的全部证据信道，保持物理世界和 Q 不变；不能从另一 Key、I 或 Bridge 补回缺失信息。MI2 未通过观察隔离前，不冻结为有效 L2。
6. **整条序列是否可执行：** 所需 I 的完整单房间轨迹或合格切段、共享对象、状态边界、稳定门状态，以及全部 Bridge 的距离与碰撞检查、完整回放全部通过，才进入批量采集。不能只因 room_id 不同就接受远距离间隔任务。

分别报告记忆选择正确与物理执行成功。反事实变体、同源 K/Q 及只改变 I 顺序的实例须成组划分训练/测试，避免泄漏。本次完成文档与静态资产核对，尚未完成这些动态验收。
